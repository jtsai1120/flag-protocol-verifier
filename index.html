Flag protocol verifier

Give it a flag fault-tolerant error-correction protocol. It checks whether any run with up to ⌊(d−1)/2⌋ faults leaves the decoder unable to correct the error.

Try it in your browser Get started Results View on GitHub

What it checks

A flag protocol measures stabilizers with circuits that use extra flag qubits. It then decides adaptively, from the syndromes and flags it has seen, when to stop and what to decode. The protocol is fault tolerant if every run with at most t = ⌊(d−1)/2⌋ faults ends in a state the decoder can correct.

The verifier tests exactly that, following Formal Verification of Flagged Fault-Tolerant Error Correction Protocols: a protocol is fault tolerant exactly when it is valid and correctable. It checks three things.

  • Circuit validity. Every extraction circuit measures the generators it declares, lets data errors through unchanged, has no random outcome, and leaves the encoded state alone.
  • Correctability. For every execution path and every measurement record along it, the verifier builds the set of data errors that an input error of weight r and s faults can leave behind, with r + s ≤ t. That set must not hold two errors E1, E2 with the same syndrome whose product is a non-trivial logical operator, an element of N(S)∖S. Such a pair means correcting one error damages the encoded state under the other.
  • Protocol validity. Control-flow bugs: a terminal that decodes needs all remaining errors to share one syndrome (Condition 1) or the path to end in enough identical, unflagged full rounds for the faults it has exposed (Condition 2); a terminal that ends without decoding needs every error from s faults to lie within weight s of the code space (Condition 3). Flag bugs: the circuits of every such repeated suffix must satisfy the flag condition it relies on.

Every two-qubit gate is a fault location, where a fault is any Pauli on the gate’s two qubits. Single-qubit gates, preparations and measurements are taken as fault free, which is the model these protocols assume. Error sets are kept as decision diagrams through SPBDD, so the verifier never lists errors one by one.

A worked example

The smallest protocol worth checking measures the four generators of the [[5,1,3]] code once, with one unflagged syndrome qubit per generator, and decodes what it saw:

gvar:
    bit[4] s = ⊥;

tc:
    1: (s != ⊥)

af:
    while(!tc) {
        (s,) = FSE_b();
    }

tp:
    1: { decode(mr[s]); }

One round without flags is not fault tolerant, and the verifier says why:

$ ./build/ftec-verify protocol.fpdl
protocol        : my_protocol
code            : [[5,1,3]], tau = 1
input errors    : r + s <= tau
paths reached   : 1 of 1
records reached : 16
circuits run    : 1

correctability
11 unprotected path(s); first failure at t = 1

  path 0  t=1  record=0000
        IIIIZ and IIYZX share syndrome 0100 but differ logically (00 vs 11)
  ...

protocol validity
terminal records: Cond 1 2, Cond 2 0, Cond 3 0
control-flow bugs: 1 path(s), 14 terminal record(s)
  path 0  decode  record=0000
        Cond 1: IIIII and IIIZI differ on XZZXI; Cond 2: w = 0 needs 2 repeated rounds, the record has 1
flag bugs       : 0 circuit(s)

FTEC            : rejected

Take the first line. With one fault, the round can measure 0000 and leave either IIIIZ or IIYZX on the data. The second is a hook error: one fault at a gate part-way through a check, whose part on the syndrome qubit spread to the data qubits the check couples after it. The two errors have the same syndrome, 0100, but differ by a logical operator, so no correction is right for both. This is the failure flag qubits exist to catch.

The control flow is not valid either. After one round that measured 0000, the data may be clean or may carry IIIZI, left by a fault after the check that would have seen it; the two have different syndromes, and with a single round the decoder has nothing to tell them apart by (Condition 1 fails, and one round is not a repeated suffix, so Condition 2 cannot hold). The flagged protocols in the repository, such as Chao & Reichardt’s, pass all three checks.

Get started

You need g++ with C++20, make and git. Nothing else is installed system-wide: the build fetches SPBDD, and SPBDD fetches BuDDy.

  1. Clone the repository

    git clone https://github.com/jtsai1120/flag-protocol-verifier
cd flag-protocol-verifier

  2. Build

    make fetches fmlab-iis/spbdd at a pinned commit and builds it with its own Makefile. It keeps only libspbdd.a (BuDDy included) and the public headers under third_party/spbdd/, then builds build/ftec-verify.

    make

  3. Test

    This parses every protocol and circuit. It then verifies each distance-3 protocol with all four E1E2 methods and compares the verdicts against the recorded ones.

    make check

  4. Verify a protocol

    ./build/ftec-verify "protocols/CR17_[[5,1,3]]/CR17_[[5,1,3]].fpdl"
./build/ftec-verify "protocols/CB18_[[17,1,5]]_plain/CB18_[[17,1,5]]_plain.fpdl" --fqcv=table

Options

OptionDefaultWhat it does
--fqcv=METHODimageHow the final E1E2 query is answered: bruteforce, table, image or square. All four give the same verdict.
--bound=NsearchedFix the bounded-model-checking bound. Without it, the bound doubles from 16 until the symbolic expansion is complete.

To build against another SPBDD, use make SPBDD_REF=<commit> after make distclean, or make SPBDD_SRC=/path/to/spbdd to use a checkout as it is.

How it works

The circuits are checked first

Before anything runs, every extraction circuit is checked against its declaration by propagating signed Pauli operators through the ideal circuit. Each syndrome measurement, traced back to the start, must observe the generator that g: lists for that bit; every measurement of any ancilla must observe a stabilizer, so that its outcome is not random; data errors must come out as themselves up to a stabilizer; and the logical operators must come through unchanged. A circuit wired to the wrong qubit, using the wrong Pauli, measuring in the wrong basis, reading its bits in the wrong order, or scheduled so that an outcome is random is rejected, with the line and what it measures instead. Without this check, such a circuit would be verified as written and could still pass.

Paths become a trie

The FPDL front end expands the protocol symbolically into every path its control flow allows. It doubles the bound until no path is cut short, and checks that the terminal conditions are mutually exclusive. Paths share long prefixes, so they are merged into a trie and walked depth first. Each extraction circuit then runs once per prefix instead of once per path, and only the states on the current root-to-node chain are alive.

States are families of Pauli sets

A state is the family of error sets indexed by (r, s): input weight r and fault count s, with r + s ≤ t. Running a circuit propagates every set through its gates. At each two-qubit gate, the (r, s) set spawns into the (r, s+1) set, and each measurement splits the state by outcome. Two outcomes are different records, so they never merge. A repeated state is recognised by its diagram’s root node and its result reused.

Validity at the terminals

Conditions 1 and 3 are read off the state itself: no generator may split the union of its sets, and each (r, s) set must lie inside the errors of weight at most s times the stabilizer group. Condition 2 is read off the records of a path: each is regrouped into rounds and the faults it exposes are counted, and the path has the form of Condition 2 when every record ends in the same repeated suffix. The circuits of that suffix are then checked for the flag condition by running each alone with up to k faults. Every bug is reported with a counterexample.

The final E1E2 query

At each terminal, SPBDD’s code::find_qec_cond_violation looks for two errors with the same syndrome whose product lies in N(S)∖S. It offers four ways to answer, with identical verdicts and different costs:

MethodHow
bruteforceEnumerate the error set and multiply every pair.
tableEnumerate the set once, keyed by syndrome.
imageDynamic programming over the layers of the set’s diagram.
squareBuild E·E and intersect it with N(S)∖S, which is built once per code.

The query is cheap; propagation is not. On the generated CB18 protocols below, the final query takes about half a percent of the run.

Formats

A protocol is a directory with one .fpdl file and the OpenQASM circuits it refers to. Relative paths in the .fpdl resolve against its own directory.

.fpdl — the protocol

FPDL, the Flag Protocol Description Language, describes a protocol in six blocks:

code[[n,k,d]] and the stabilizer generators, dense ([X,Z,Z,X,I]) or sparse ([X3, X4, X5, X6], one-based).
seThe extraction circuits: QASM file, data / syndrome / flag registers (qd, qm, qf), the generators measured (g), and for flagged circuits the #-flag claim.
gvarGlobal variables: counters, bit vectors that start as ⊥, and measurement records mr.
tcNumbered terminal conditions. They must be mutually exclusive.
afThe adaptive flow: rounds of extraction calls such as (s, f) = FSE_f(); and the updates between them.
tpOne terminating policy per terminal condition, ending in decode(...) or end().
 
protocol CB18_[[25,1,5]]_plain:
    code:
        [[25,1,5]]
        [[Z1, Z6], [Z2, Z3, Z7, Z8], ...]
    se:
        FSE_f {
            file: "./FSE_f.qasm"
            qd: data
            qm: syn
            qf: flag
            g: [[Z1, Z6], [Z2, Z3, Z7, Z8], ...]
            #-flag: 2
        }
    ...
    tc:
        1: ((n_c_same == 3 - n_diff - 1 and n_c_same != 0) and n_flag == 0)
        2: (n_diff == 2 and n_flag == 0)
        ...

The full grammar, typing rules and static checks are in docs/FPDL.md.

.qasm — the circuits

OpenQASM 3.0 with the Clifford gates the error model needs:

idxyzhssdgcxcyczresetmeasurebarriergate (inlined)

Declare qubit and bit registers. A measurement such as m[0] = measure syn; binds the classical bit to the qubit it reads, so the verifier finds the syndrome and flag records from the registers named in qm and qf.

// g0 = Z2 Z3 Z7 Z8; flag f0.
reset syn; h syn; reset flag;
cz syn,data[1]; cx syn,flag; cz syn,data[2];
cz syn,data[6]; cx syn,flag; cz syn,data[7];
h syn; m[1]=measure syn; f[0]=measure flag;

Generating larger CB18 protocols

tools/gen_cb18_surface.py writes the general t-fault-tolerant protocol of Chamberland & Beverland, Section 3, for a rotated surface code. It produces both the FPDL file and the circuits, for a square d×d lattice or a rectangular d×C one. At d=5 its output is identical to the hand-written [[25,1,5]] protocol.

tools/gen_cb18_surface.py 5 --cols 9 --out protocols   # [[45,1,5]] on a 5×9 lattice
tools/gen_cb18_surface.py 7 --out protocols            # [[49,1,7]]

Playground

The playground runs the verifier in your browser as WebAssembly, compiled from the same sources as the native build. Nothing is uploaded.

Pick any bundled protocol or add your own .fpdl and .qasm files, edit them, and verify. Distance-3 protocols finish instantly. The distance-5 ones run for several minutes, about two and a half times their native time.
