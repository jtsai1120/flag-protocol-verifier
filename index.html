Flag protocol verifier

Give it a flag fault-tolerant error-correction protocol. It checks whether any run with up to ⌊(d−1)/2⌋ faults leaves the decoder unable to correct the error.

Try it in your browser Get started View on GitHub

What it checks

A flag protocol measures stabilizers with circuits that use extra flag qubits. It then decides adaptively, from the syndromes and flags it has seen, when to stop and what to decode. The protocol is fault tolerant if every run with at most t = ⌊(d−1)/2⌋ faults ends in a state the decoder can correct.

The verifier tests exactly that. For every execution path of the protocol and every measurement record along it, it builds the set of data errors that up to t faults can leave behind. It then asks whether that set holds two errors E1, E2 that the record cannot tell apart, yet whose product E1E2 is a non-trivial logical operator, an element of N(S)∖S. Such a pair means correcting one error damages the encoded state under the other. If no reachable set contains such a pair, the protocol is fault tolerant.

Every two-qubit gate is a fault location, where a fault is any Pauli on the gate’s two qubits. Single-qubit gates, preparations and measurements are taken as fault free, which is the model these protocols assume. Error sets are kept as decision diagrams through SPBDD, so the verifier never lists errors one by one.

A worked example

The flag-sharing protocol for the [[5,1,3]] code from Liou & Lai (arXiv:2407.00607), in its fully parallel [2,2]T arrangement, runs one flagged extraction round. It stops if nothing fires; otherwise it runs one unflagged round and decodes from all three results:

af:
    while(!tc) {
        (m,f) = FSE_f();
    }

tp:
    1: { end(); }
    2: {
        bit[4] mp = ⊥;
        (mp,) = FSE_b();
        decode(mr[m, f, mp]);
    }

Verifying it finds one record that breaks the protocol:

$ ./build/ftec-verify "protocols/LL25_[[5,1,3]]_[2,2]^T/LL25_[[5,1,3]]_[2,2]^T.fpdl"
protocol        : LL25_[[5,1,3]]_[2,2]^T
code            : [[5,1,3]], tau = 1
paths reached   : 2 of 2
records reached : 153
circuits run    : 36

1 unprotected path(s); first failure at t = 1

  path 1  t=1  record=0001,01|0011
        IIZIX and IZIIZ share syndrome 0001 but differ logically (01 vs 11)

Read the record left to right: the flagged round measured syndrome 0001 with flags 01, and the unflagged round measured 0011. A single fault can produce this record with either IIZIX or IZIIZ on the data. The two errors differ by a logical operator, so whichever one the decoder corrects, the other one is left as a logical error. The same protocol in its non-transposed [2,2] arrangement fails on four records; the [1,1,1,1]T arrangement passes.

Run this example in the playground.

Get started

You need g++ with C++20, make and git. Nothing else is installed system-wide: the build fetches SPBDD, and SPBDD fetches BuDDy.

  1. Clone the repository

    git clone https://github.com/jtsai1120/flag-protocol-verifier
cd flag-protocol-verifier

  2. Build

    make fetches fmlab-iis/spbdd at a pinned commit and builds it with its own Makefile. It keeps only libspbdd.a (BuDDy included) and the public headers under third_party/spbdd/, then builds build/ftec-verify.

    make

  3. Test

    This parses every protocol and circuit. It then verifies each distance-3 protocol with all four E1E2 methods and compares the verdicts against the recorded ones.

    make check

  4. Verify a protocol

    ./build/ftec-verify "protocols/CR17_[[5,1,3]]/CR17_[[5,1,3]].fpdl"
./build/ftec-verify "protocols/CB18_[[17,1,5]]_plain/CB18_[[17,1,5]]_plain.fpdl" --fqcv=table

Options

OptionDefaultWhat it does
--fqcv=METHODimageHow the final E1E2 query is answered: bruteforce, table, image or square. All four give the same verdict.
--bound=NsearchedFix the bounded-model-checking bound. Without it, the bound doubles from 16 until the symbolic expansion is complete.
--max-paths=N5000Give up past this many symbolic paths.
--firstoffStop at the first unprotected path.
--dagoffPrint the merged path structure and exit without verifying.

To build against another SPBDD, use make SPBDD_REF=<commit> after make distclean, or make SPBDD_SRC=/path/to/spbdd to use a checkout as it is.

How it works

Paths become a trie

The FPDL front end expands the protocol symbolically into every path its control flow allows. It doubles the bound until no path is cut short, and checks that the terminal conditions are mutually exclusive. Paths share long prefixes, so they are merged into a trie and walked depth first. Each extraction circuit then runs once per prefix instead of once per path, and only the states on the current root-to-node chain are alive.

States are families of Pauli sets

A state is the family of error sets indexed by fault count 0…t. Running a circuit propagates every set through its gates. At each two-qubit gate, the fault-k set spawns into the fault-(k+1) set, and each measurement splits the state by outcome. Two outcomes are different records, so they never merge. A repeated state is recognised by its diagram’s root node and its result reused.

The final E1E2 query

At each terminal, SPBDD’s code::find_qec_cond_violation looks for two errors with the same syndrome whose product lies in N(S)∖S. It offers four ways to answer, with identical verdicts and different costs:

MethodHow
bruteforceEnumerate the error set and multiply every pair.
tableEnumerate the set once, keyed by syndrome.
imageDynamic programming over the layers of the set’s diagram.
squareBuild E·E and intersect it with N(S)∖S, which is built once per code.

The query is cheap; propagation is not. On the generated CB18 protocols below, the final query takes about half a percent of the run.

Formats

A protocol is a directory with one .fpdl file and the OpenQASM circuits it refers to. Relative paths in the .fpdl resolve against its own directory.

.fpdl — the protocol

FPDL, the Flag Protocol Description Language, describes a protocol in six blocks:

code[[n,k,d]] and the stabilizer generators, dense ([X,Z,Z,X,I]) or sparse ([X3, X4, X5, X6], one-based).
seThe extraction circuits: QASM file, data / syndrome / flag registers (qd, qm, qf), the generators measured (g), and for flagged circuits the #-flag claim.
gvarGlobal variables: counters, bit vectors that start as ⊥, and measurement records mr.
tcNumbered terminal conditions. They must be mutually exclusive.
afThe adaptive flow: rounds of extraction calls such as (s, f) = FSE_f(); and the updates between them.
tpOne terminating policy per terminal condition, ending in decode(...) or end().
 
protocol CB18_[[25,1,5]]_gen:
    code:
        [[25,1,5]]
        [[Z1, Z6], [Z2, Z3, Z7, Z8], ...]
    se:
        FSE_f {
            file: "./FSE_f.qasm"
            qd: data
            qm: syn
            qf: flag
            g: [[Z1, Z6], [Z2, Z3, Z7, Z8], ...]
            #-flag: 2
        }
    ...
    tc:
        1: ((n_c_same == 3 - n_diff - 1 and n_c_same != 0) and n_flag == 0)
        2: (n_diff == 2 and n_flag == 0)
        ...

The full grammar, typing rules and static checks are in docs/FPDL.md.

.qasm — the circuits

OpenQASM 3.0 with the Clifford gates the error model needs:

idxyzhssdgcxcyczresetmeasurebarriergate (inlined)

Declare qubit and bit registers. A measurement such as m[0] = measure syn; binds the classical bit to the qubit it reads, so the verifier finds the syndrome and flag records from the registers named in qm and qf.

// g0 = Z2 Z3 Z7 Z8; flag f0.
reset syn; h syn; reset flag;
cz syn,data[1]; cx syn,flag; cz syn,data[2];
cz syn,data[6]; cx syn,flag; cz syn,data[7];
h syn; m[1]=measure syn; f[0]=measure flag;

Generating larger CB18 protocols

tools/gen_cb18_surface.py writes the general t-fault-tolerant protocol of Chamberland & Beverland, Section 3, for a rotated surface code. It produces both the FPDL file and the circuits, for a square d×d lattice or a rectangular d×C one. At d=5 its output is identical to the hand-written [[25,1,5]] protocol.

tools/gen_cb18_surface.py 5 --cols 9 --out protocols   # [[45,1,5]] on a 5×9 lattice
tools/gen_cb18_surface.py 7 --out protocols            # [[49,1,7]]

Playgrounds

Both tools run in your browser as WebAssembly, compiled from the same sources as the native build. Nothing is uploaded.

Verifier playground

Pick any bundled protocol or add your own .fpdl and .qasm files, edit them, and verify. Distance-3 protocols finish instantly. The distance-5 ones run for several minutes, about two and a half times their native time.

SPBDD playground

Write JavaScript against SPBDD’s API: build Pauli sets, push them through Clifford gates, inject faults, define a stabilizer code and ask for a QEC-condition violation. Examples are included.
